# nanoamp UI 方案对比与分平台建议 v2

> 关联：`00_materials/TUI_plan.1.md`（v1：纯 R 终端 TUI 单方案）
> 本文件目的：在 v1 的终端 TUI 之外，给出**其他可选 UI 形态**，并分别就
> **Linux 终端**与 **macOS** 给出建议与优先级。
> 本文件状态：**只做方案与选型论证，不含实现代码。**
> 实测环境：macOS arm64（Darwin 24.6.0）、系统 R 4.6.1（`aarch64-apple-darwin23`）、
> 验证环境 R 4.5.3（`aarch64-apple-darwin20`，`tmp/nanoamp-env`）

---

## 1. 本轮新增的实测结论（决定了后面的选型）

| 发现 | 实测证据 | 对选型的意义 |
|---|---|---|
| **两个 R 都自带 `tcltk`，且 macOS 上编译了 `aqua`（原生窗口）** | `requireNamespace("tcltk")` 为 TRUE；`capabilities()[["aqua"]]` 为 TRUE | 可以**零新增运行时依赖**做出真正的图形窗口应用（不是浏览器、不是模拟终端） |
| **Tk/ttk 真的能起窗口并用主题控件** | `tclVersion()` = 8.6.13（conda R）/ 8.6（系统 R）；`tktoplevel()` + `tklabel()` + `tkbutton()` + `ttkcombobox()` + `tkwinfo("children",".")` 全部成功，`tkdestroy()` 正常 | Tcl/Tk 路线不是纸面可行，本机已跑通 |
| **Swift + Xcode CLT 存在** | `/usr/bin/swift`、`xcrun`、`codesign` 均在；`xcode-select -p` = `/Library/Developer/CommandLineTools` | 原生 SwiftUI `.app` 在技术上可做，但需签名/公证 |
| **系统 Python 3.13 自带 tkinter 8.6** | `import tkinter` 成功 | Python 侧也有 GUI 能力，但引入第二语言，与既有决策冲突 |
| **Shiny 依赖链目前完全没有装** | `httpuv`/`later`/`promises`/`shiny` 在两个 R 里都是 FALSE（CRAN 上均存在） | 本地 Web UI 路线需要新增 4 个包和编译，成本不再是"顺手" |
| **`fzf` 本机未安装** | `command -v fzf` 为空 | 只能作为可选增强，不能作为依赖 |

## 2. 候选 UI 形态（6 种）

命名约定：C1–C6 便于后续引用。

| 编号 | 形态 | 技术 | 呈现 |
|---|---|---|---|
| **C1** | 终端 TUI | 纯 R + ANSI + `stty` raw mode（v1 方案） | 终端全屏界面 |

## 4. Linux 终端场景的建议

### 4.1 现实约束

Linux 侧用户（学生会一点命令行、生信同学）**本来就在终端里工作**。对他们来说，
开浏览器或开窗口不是"更方便"，而是"多了一步"。真正的痛点是：

1. 长文件名手敲易错；
2. 参数多、不知道该选哪个；
3. 结果表 `cat` 出来看不懂。

这三件事**全部可以在终端内解决**，不需要 GUI。

### 4.2 建议：C1 为主 + C2 为辅，C4 不推荐

| 优先级 | 方案 | 理由 |
|---|---|---|
| **P0** | **C1 终端 TUI**（v1 方案原样推进） | 终端原生；无新增依赖；SSH 可用；同时兼容 Linux arm64 |
| **P0** | **C2 选择器增强 CLI**（与 C1 共用同一套 manifest 读取与参数校验） | 成本只要 2–3 天，却直接消灭"手敲长文件名"；对脚本用户比 TUI 更合口味 |
| P2（可选） | C3 R+Tk 窗口 | 仅当出现"Linux 桌面用户"这一真实需求时再做（例如教授在 Ubuntu 工作站上用） |
| 不推荐 | C4 本地 Web | 终端用户需额外开浏览器；且当前 Shiny 链 4 个包全未安装，成本不再低；远程/多人共享场景才值得（见 §7 决策树） |
| 不适用 | C5 / C6 | 平台绑定 |

### 4.3 C2 的具体形态（Linux 上最划算的一件事）

三种由弱到强的实现，建议做到中间那档：

```bash
# 第一档：补全与提示（零依赖）
nanoamp samples list                      # 列出 dataset/sample 短名与真实路径
nanoamp call --sample TSM20260826/E4-3 \  # 直接用短名，内部查 manifest.tsv
              --ref self --mode A

# 第二档：交互选择（零依赖，行式菜单，复用 v1 的 --plain 渲染器）
nanoamp pick --dataset TSM20260826        # 编号菜单选 sample，输出一条可直接复制的 call 命令
nanoamp run                               # = pick + 参数向导 + 执行，本质是 C1 的行式模式

# 第三档：fzf 增强（可选，命中 fzf 时启用；未安装则自动回落到第二档）
nanoamp call --sample "$(nanoamp samples list --short | fzf)" ...
```

要点：**第一、二档不引入任何依赖**，第三档只做"有则更好"。同时建议补 shell 补全脚本
（bash/zsh 各一份，放 `02_code/cli/completions/`），让 `--mode`、`--dataset`、
`--sample`、`--aligner` 都能 Tab 补全。

### 4.4 Linux 上需要注意的点

1. **`--sample` 短名解析应下沉到 R 层**，而不是只在 shell 里拼路径——否则 `batch`
   与 TUI 都要各自实现一遍，违背"一套算法一个外壳"。建议在 `R/io.R` 增加
   `resolve_sample(dataset, sample, role)`，读取 `01_data/manifest.tsv`。
2. `tk` 在部分最小化 Linux 安装里缺失（`apt install tk` / conda `tk`）。若未来做
   C3，必须像 minimap2 一样做"能力探测 + 降级到 C1"，不能让缺 `tk` 变成崩溃。
3. 终端兼容性差异比 macOS 大（tmux/screen、TERM 变体、真彩色支持不一），
   v1 方案里的 `NO_COLOR`、小终端提示、非 UTF-8 降级都必须真正实现。

## 5. macOS 场景的建议

### 5.1 现实约束

macOS 侧的目标用户是**教授本人**。这类用户的核心诉求不是"强大"，而是
**不要让我打开终端、不要让我敲路径、不要让我读 TSV**。因此：

- C1（终端 TUI）对他仍然有门槛——他得先找到"终端"这个 App；
- C2 对他基本无用；
- **真正合适的是"双击就能开的窗口应用"**。

好消息是：本机实测证明 `tcltk` + `ttk` 可以直接在 macOS 上开出**原生 Aqua 外观**
的窗口，而且**不需要安装任何东西**（R 自带）——这比 SwiftUI 便宜一个数量级，
比 Shiny 少 4 个依赖。

### 5.2 建议：C3 为主 + C1 为辅，C5 作为长期选项

| 优先级 | 方案 | 理由 |
|---|---|---|
| **P0** | **C3 R+Tk 原生窗口**，并**打包成 `.app`** 使其可双击 | 零新增依赖；aqua 原生外观；本机已实测 Tk 可用；一套 R 代码即产出 |
| P1 | **C1 终端 TUI** | 给会命令行的学生/同事；ssh 进服务器时唯一可用形态；与 C3 共享同一状态机 |
| P1 | **C6 osascript 增强** | 成本 1–2 天，立刻能解决"选文件"和"跑完通知我"，可先于 C3 落地 |
| P2（长期） | **C5 SwiftUI `.app`** | 只有在 Tk 版本"不够好看/不够稳"时才值得；代价是 15–25 天 + 签名/公证 + 每次 R 侧变更要同步 Swift 壳 |
| 不推荐（现阶段） | **C4 本地 Web** | 若未来需要"多人共享 / 远程服务器 / 手机看结果"再启用（见 §7） |

### 5.3 关于 `.app` 打包：两条路线

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **脚本壳（推荐先做）** | `nanoamp.app/Contents/MacOS/nanoamp` 是一个 shell 脚本，内部 `exec Rscript ... --gui`；`Info.plist` 声明图标与名称 | 30 分钟可做；不需要 Xcode 工程；R 代码改了立即生效 | 首次打开可能触发 Gatekeeper（未签名/未公证），需要右键→打开一次 |
| 原生编译 | SwiftUI 前端，或 R 侧用 `R CMD build --binary` 思路打包 | 体验最原生 | 需 Apple Developer 账号做公证，否则同样被拦；维护成本高 |

**重要提醒**：macOS 的 Gatekeeper 只认"签名 + 公证"，**不因语言而网开一面**。
所以"用 Swift 写就避免了签名问题"是个误解——两条路线的分发摩擦是一样的。
既然摩擦相同，就该选成本低 5 倍的那条（Tk）。

### 5.4 macOS 上需要注意的点

1. **R 的来源会影响 Tk 外观与可用性**：系统 R（`/usr/local/bin/R`，已编译 aqua）与
   conda R 都能起 Tk，但依赖的 Tcl/Tk 版本不同（8.6 vs 8.6.13）；`.app` 应绑定
   一个确定的 R（建议 conda 环境或系统 R 二选一，并在启动脚本里检测）。
2. **不要用 osascript 当主界面**：它能做文件选择和通知，但做不了结果表格与参数校验，
   只适合做"外壳增强"。
3. **Retina/缩放**：Tk 8.6 在高分屏下字体可能偏小，需显式设置 `tk scaling`。
4. **后台长任务**：macOS 上用户容易以为"没反应"，需要进度条 + 完成后 `osascript`
   系统通知（这正是 C6 的价值）。

## 6. 统一架构建议：一个核心，多个外壳

C1 与 C3 都不需要重写分析逻辑，也不应该各写一套界面逻辑。建议把 v1 里的分层再抽一层：

```text
                    ┌──────────────────────────────────────────┐
                    │  UI 核心（纯函数，无 I/O）                 │
                    │  状态机 · 参数校验 · 键位/事件派发         │
                    │  · 表格布局与截断 · 结果模型               │
                    └───────┬───────────────┬──────────────────┘
                            │               │
             ┌──────────────▼───┐   ┌───────▼──────────────┐
             │ C1 终端后端       │   │ C3 Tk 后端            │
             │ ANSI 渲染 + raw 键 │   │ ttk 控件 + 事件循环    │
             └──────────┬───────┘   └───────┬──────────────┘
                        └────────┬──────────┘
                    ┌────────────▼─────────────────────────────┐
                    │ run_haplotype_analysis()  ← 零改动        │
                    └──────────────────────────────────────────┘
```

**收益**：参数校验、样本解析、结果模型只写一遍；终端与窗口两种呈现共享同一份业务逻辑；
测试只需覆盖 UI 核心（纯函数，可在无显示环境下跑）。

**代价与警惕**：多外壳是"架构上正确、执行上危险"的典型——一次做四五个前端必然全部
半成品。因此**必须排优先级分批做**（见 §8），不要并行开工。

## 7. 决策树（按"用户在哪、怎么用"选）

```text
用户是否愿意打开终端？
├─ 愿意（学生、生信同学、ssh 进服务器）
│   ├─ 在本地 Linux/macOS 终端  ──────────────► C1 终端 TUI
│   └─ 在服务器上通过 ssh/端口转发
│       ├─ 只需自己用  ──────────────────────► C1（ssh 唯一可靠形态）
│       └─ 需要多人共享/手机看 ──────────────► C4 本地 Web + 端口转发
└─ 不愿意（教授本人、实验人员）
    ├─ 只在 macOS 上  ───────────────────────► C3 Tk 窗口 + .app 双击
    │   └─ 若对观感有明确不满 ───────────────► C5 SwiftUI（长期）
    ├─ 只在 Windows 上  ─────────────────────► 交由姊妹仓库决策（建议同做 Tk 以保持一致）
    └─ 首次接触、只想"选个文件跑一下" ────────► C6 osascript 先行（1–2 天见效）
```

## 8. 建议的推进顺序（与 v1 排期合并）

| 阶段 | 内容 | 人日 | 交付判据 |
|---|---|---|---|
| **S0** | C1 方案的 P0 可行性验证（raw mode、终端恢复） | 0.5–1 | 见 v1 第 8 节 P0 |

| **S3** | **C6 osascript 外壳增强**（文件选择 + 完成通知） | 1–2 | macOS 上"选文件→跑→弹通知"可用 |
| **S4** | **C3 R+Tk 窗口**（复用 S2 的 UI 核心） | 4–6 | 双击 `.app` 能用鼠标完成主场景 |

| **S6（可选）** | C4 本地 Web（仅当出现远程/多人需求） | 5–7 | 端口转发后浏览器可完成主场景 |

## 9. 风险与需要澄清的问题

### 9.1 风险

| # | 风险 | 对策 |
|---|---|---|
| R1 | **C3 与"C 端 GUI 已移交姊妹仓库"存在定位重叠**：如果 macOS 侧做 Tk 窗口，Windows 侧是否也该有对等体验？否则同一个产品在三个平台上是三种形态 | **需先澄清（见 9.2 问题 1）**，再决定 C3 是否做 |
| R2 | Tk 界面在不同平台观感差异大（macOS aqua 好看，Linux 需装 `tk` 且主题依赖桌面环境） | Linux 上把 C3 定位为可选增强；主推 C1 |
| R3 | 多前端并行导致全部半成品 | 严格串行排期（§8）；先交付 S1–S3 |
| R4 | Gatekeeper 拦截（两条 macOS 路线都一样） | 文档写清"右键→打开"；如需正式分发再评估 Apple Developer 账号 |
| R5 | C4 若做成"对外服务"会引入安全面（端口、文件读取、注入） | 只绑定 `127.0.0.1` + 一次性 token；明确不做公网部署 |
| R6 | 依赖 `fzf`/`tk`/`shiny` 造成的可用性分叉 | 全部走"能力探测 + 自动降级"；主路径永远不依赖它们 |

### 9.2 需要你确认的问题

1. **产品边界**：macOS 侧的窗口应用属于本仓库，还是与 GUI 一样归姊妹仓库
   `a_09_18_26_mapping_programs_dev_for_win`？这直接决定 C3/C5/C4 是否在范围内。
2. **教授的实际操作系统**：如果教授用 macOS，C3+`.app` 应提到 S1 之前；如果用
   Windows，本仓库只需交付 C1/C2。
3. **是否需要远程/多人共享**？若是，C4 的优先级要上调，并且需要先定安全边界。
4. **是否接受为 C4 引入 `shiny`/`httpuv` 依赖**（当前 4 个包全未安装）？
5. **C5 是否在任何情况下都在范围内**？若不在，可明确写入"非目标"，避免后续反复。
6. **Linux 侧是否真的存在"桌面 GUI 用户"**？如果没有，C3 在 Linux 上可以直接不做。

## 10. 结论摘要

| 平台 | 首选 | 次选 | 不做（现阶段） |
|---|---|---|---|
| **Linux 终端** | **C1 终端 TUI** | **C2 选择器 + 短名 + 补全**（性价比最高，先做） | C4 本地 Web（无真实需求，且依赖未装）；C5/C6 不适用 |
| **macOS** | **C3 R+Tk 原生窗口 + `.app` 双击**（零新增依赖，本机已实测 Tk 可用） | **C6 osascript 增强**（1–2 天见效）；C1 供 ssh/技术用户 | C4 本地 Web（暂无需求）；C5 SwiftUI（成本高 5 倍，摩擦相同，长期备选） |
