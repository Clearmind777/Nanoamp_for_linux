## 1. 背景与目标

### 1.1 为什么还要一个 TUI

委托方的诉求是"每个小文库都让生信同学手工分析，数量太多，不可持续"。目前仓库已经
能做到：一条命令跑完一个样本（`nanoamp call`）、一张表跑完一批（`nanoamp batch`）、
环境自检（`nanoamp doctor`）。

对**会敲命令的人**这已经够了。但对委托里"不太懂生信的生物学教授"这类用户，仍然存在
三个实际门槛：

1. **参数有 15 个以上**，且方案 A/B/C 该用哪个、`--min-freq` / `--identity-cutoff`
   该调多少，需要读文档才知道；
2. **文件名太长**。公司交付的文件名形如
   `E4-3_TSM20260826-020-01254_20260827-020-BAN05-5_H08.fastq`，手敲极易出错。
   仓库虽然有 `01_data/manifest.tsv` 提供短名映射，但目前只有 `awk`/R 片段能读它；
3. **结果要看懂**。`haplotypes.tsv`、`variants.tsv`、`qc.tsv` 三张表在终端里
   `cat` 出来是混乱的，需要"挑一个样本 → 看排名前几的序列 → 看这条序列带了哪些变异"
   这种浏览动作。

GUI 已经在 `work_report.7.md` 那轮移除，且明确由姊妹仓库
`a_09_18_26_mapping_programs_dev_for_win` 承担。因此本方案**不恢复 GUI，也不做 Web**，
而是在现有 CLI 之上加一层**终端交互界面（TUI）**：同一个算法核心、同一套参数契约，
只是把"敲命令"换成"选菜单"。

### 1.2 目标（按优先级）

| 优先级 | 目标 | 验收标准 |
|---|---|---|
| P0 | 不查文档、不手敲长文件名就能跑完一个样本 | 从启动到产出 `haplotypes.tsv` 全程只用方向键/回车，样本从 manifest 里选 |
| P0 | 复用现有算法核心，不产生第二套实现 | TUI 内调用 `run_haplotype_analysis()`；`R/` 下分析代码零改动 |
| P1 | 能看懂结果 | 结果页展示 top-N 单倍型（占比 + 变异摘要）、QC 摘要、并可下钻到变异明细 |
| P1 | 非交互环境不崩 | 无 TTY / `TERM=dumb` / 管道输入时给出明确提示，或降级到行式模式 |
| P2 | 批量跑 | 选择数据集与多个样本，串行执行并汇总，复用 `batch_summary.tsv` 契约 |
| P2 | 可测试 | 布局、按键派发、状态机、参数校验都有纯函数单测；TUI 逻辑纳入 `R CMD check` |

### 1.3 明确的非目标

- 不做 GUI / Web / 手机端（GUI 属姊妹仓库职责）；
- 不做 basecalling、不做比对算法本身的重写；
- 不做"打开 BAM 浏览覆盖度"这类全功能基因组浏览器（超出委托范围）；
- 不引入 conda 之外的重型运行时（见第 3 节技术选型）；
- 不改动 `02_code/shared/` 里的参数与输出契约（TUI 只是消费者）。

## 2. 用户与典型场景

### 2.1 用户画像

| 用户 | 场景 | 对 TUI 的期待 |
|---|---|---|
| 教授本人（不写代码） | 拿到一个新交付的 FASTQ，想知道"有多少是我要的序列" | 全程选单；参数用默认值；结果能一眼看懂 |
| 组内学生会一点命令行 | 想快速比较不同 `--min-freq` 下的结果 | 能改参数、能重跑上一次、能看到参数被记录在 `run_manifest.json` |
| 生信同学 | 批量处理一个批次 | 能一次选多个样本，最好直接看到汇总表 |

### 2.2 主场景（贯穿后续设计）

> 教授拿到 `01_data/test_data/TSM20260826-020-01254/` 这批新数据，想知道 E4-3
> 这个样本里目标序列占多少、还有哪些别的序列。

期望路径：

```text
启动 nanoamp tui
  → 样本页：方向键选 dataset=TSM20260826 → sample=E4-3（显示真实文件名与 reads 数）
  → 参数页：显示 mode=A（推荐）、top_n=20、min_freq=0.02，全部取默认值，直接下一步
  → 输出页：默认 04_results/tui/TSM20260826/E4-3/mode_A，回车确认
  → 运行页：进度（比对 → 变异发现 → 计数）+ 实时日志
  → 结果页：H1 占 40.6%（与参考一致）、H2 占 27.7%（135C>T;147delT;220delG）…
           按 Enter 看这条单倍型的变异明细，按 e 导出，按 q 返回
```

### 2.3 次场景

- **S2 换参考**：同一 reads 分别对 `reference.self` 与 `reference.wt` 跑，比较结果
  （功能测试脚本已经在做这件事，TUI 应把这个能力暴露给用户）；
- **S3 批量**：选定整个 dataset（如 `ZNF8` 的 16 个样本）→ 串行跑 → 汇总页显示每样本
  top1 占比与状态，可导出 `batch_summary.tsv`；
- **S4 环境自检**：TUI 内一个"环境"页，等价于 `doctor` 输出（平台、依赖目录、
  R 包、minimap2 路径与版本），供排障使用。

## 3. 技术选型

### 3.1 候选与结论

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 纯 R + ANSI + `stty` raw mode** | 与现有 CLI 同语言；直接调 `run_haplotype_analysis()`；无进程间开销；四平台一致；不新增运行时 | 按键读取需自己封装；Windows 终端行为需单独处理；滚动/换行要自己做 | **推荐** |
| B. R + `cli`/`crayon` 只做着色与进度 | 已有 `cli` 是传递依赖；进度条现成 | 仍不提供交互式选择与按键处理，选择要自己写 | **作为 A 的补充**（渲染与进度） |
| C. `fzf` 之类的现成选择器 | 选择体验好 | 本机未安装；四平台可用性不保证；仍是"外挂" | 列为**可选增强**，不作为依赖 |
| D. 换 Python/Rust/Go 写 TUI 壳 | TUI 生态成熟（如 Textual、ratatui） | 引入第二种语言与第二套运行时；违背"一套算法一个外壳"；Python CLI 路线此前已取消 | 不采用 |
| E. 恢复 Shiny/GUI | 表现力最强 | 已被明确移除，且属姊妹仓库职责 | 不采用 |

**结论：方案 A 为主、B 为补充、C 为可选增强。**

### 3.2 为什么坚持在 R 里做

1. **一套算法一个外壳**（`02_code/ARCHITECTURE.md` 设计原则 1）。TUI 直接
   `run_haplotype_analysis(...)`，不跨进程、不解析 stdout，参数与返回结构天然一致；
2. **参数只有一份定义**。默认值来自 `nanoamp_defaults()` / `02_code/shared/params/default_params.json`，
   校验规则来自 `R/utils.R`，TUI 不重复定义；
3. **零新增运行时依赖**。不动 `Depends`/`Imports` 的运行时门槛；四个平台的安装路径
   与 `README.md` 现有两条路径（conda / `install_r_deps.R`）完全不变；
4. **测试与 CI 复用现状**。`make test` / `make check` 已经跑得通，TUI 逻辑以纯函数
   形式纳入其中即可。

### 3.3 依赖策略

| 依赖 | 用途 | 处理 |
|---|---|---|
| base R（`readBin`/`cat`/`system`） | 输入读取、渲染、`stty` 控制 | 无新增 |
| `cli` | 着色、`cli_progress_bar` 进度、`cli_rule` 分隔线 | 已在验证环境与传递依赖中出现；建议**显式列入 `Suggests`** 并做能力探测（没有则退化为纯 ASCII） |
| `crayon` | 颜色 | 同上，二选一即可，优先 `cli` |
| `fzf` | 命令行式快速选择 | **不依赖**；仅当 `Sys.which("fzf")` 命中且用户显式开启时启用 |

原则：**任何一个可选包缺失，TUI 仍须可用**（降级为无颜色 + 纯 ASCII 边框 + 行式模式）。

## 4. 交互设计

### 4.1 页面结构

```text
                    ┌──────────────────────────────────────────┐
                    │ nanoamp TUI            macos-arm64  0.1.0 │  ← 顶栏：平台/版本
                    ├──────────────────────────────────────────┤
                    │ ① 样本  ② 参考  ③ 参数  ④ 输出  ⑤ 运行  ⑥ 结果 │  ← 步骤条
                    ├──────────────────────────────────────────┤
                    │                                          │
                    │            （当前页内容区）                │
                    │                                          │
                    ├──────────────────────────────────────────┤
                    │ ↑↓ 选择  Enter 确认  Esc 返回  ? 帮助  q 退出 │  ← 底栏：上下文快捷键
                    └──────────────────────────────────────────┘
```

页面清单：

| # | 页面 | 内容 | 关键交互 |
|---|---|---|---|
| 0 | 欢迎/环境 | 版本、平台、minimap2 解析路径、缺失依赖告警 | `Enter` 开始；`d` 看完整 doctor；有致命缺失时给出修复命令 |
| 1 | 样本 | 左列 dataset，右列 sample；显示 `reads` 路径、reads 条数（可选懒加载） | `↑↓`/`jk` 移动，`Tab` 换列，`/` 过滤，`m` 手动输入路径 |
| 2 | 参考 | 当前样本可用参考：`reference.self`、`reference.wt`；显示来源说明（`source_note`） | `↑↓` 选择，`m` 手动指定 FASTA |
| 3 | 参数 | 模式 A/B/C 单选 + 各模式相关参数；每项显示默认值与一句说明；非法值即时提示 | `↑↓` 移动，`Enter/→` 编辑，`r` 恢复默认，`s` 保存为预设 |
| 4 | 输出 | 输出目录（预填 `04_results/tui/<dataset>/<sample>/mode_<M>`）、`--no-intermediates` 开关 | `Enter` 确认并进入运行 |
| 5 | 运行 | 阶段进度（读入→比对→变异发现→过滤→计数→写盘）、已用时、实时日志尾部 | `Ctrl-C` 请求中断（写部分结果并说明）；完成后自动进入结果页 |
| 6 | 结果 | top-N 单倍型表（rank/count/proportion/是否参考/变异）、QC 摘要 | `↑↓` 选择行，`Enter` 看明细，`v` 切到变异表，`f` 切换 self/wt 结果，`e` 导出，`b` 批量 |
| 7 | 明细 | 选中单倍型的完整序列、变异列表（type/pos/ref/alt/同聚物长度/context）、95% CI | `c` 复制序列到剪贴板（平台可用时），`Esc` 返回 |
| 8 | 批量 | 多选样本 → 串行运行 → 汇总表（每样本状态、top1 占比、与公司变异表重合） | `Space` 勾选，`a` 全选，`Enter` 开始 |
| 9 | 帮助 | 键位表、模式 A/B/C 的适用场景、常见问题 | 任意键返回 |

### 4.2 键位约定

| 键 | 语义 |
|---|---|
| `↑` `↓` / `k` `j` | 上/下移动（同时支持方向键转义序列与 vim 风格） |
| `←` `→` / `h` `l` / `Tab` | 列间或页内分区间移动 |
| `Enter` | 确认 / 进入 / 下钻 |
| `Esc` | 返回上一页（不丢失已填内容） |
| `Space` | 勾选（批量页） |
| `/` | 过滤当前列表 |
| `?` | 帮助 |
| `q` | 在首页退出；在子页返回（避免误退，退出统一走首页） |
| `Ctrl-C` | 运行中：请求中断；空闲：退出 |

无障碍与兼容：

- 遵循 `NO_COLOR` 环境变量；
- 终端宽度 < 60 列或高度 < 20 行时，显示"终端过小"提示而不是渲染错位；
- 中文/变音符号按显示宽度对齐（不按字节数计算列宽）；
- 非 UTF-8 locale 时降级为纯 ASCII 边框（`+---+`、`|`）。

### 4.3 行式降级模式（无 TTY 或 raw mode 不可用）

当 `isatty(stdin())` 为假、或 `TERM` 为空/`dumb`、或用户传 `--plain` 时，不进入全屏
渲染，改用编号菜单 + 行输入：

```text
nanoamp TUI (line mode)
可用数据集：
  1) TSM20260826   (6 samples)
  2) ZNF8          (16 samples)
  3) nano_seq      (10 samples)
选择数据集 [1-3, 回车=1]:
```

该模式必须能在管道/CI 下工作，是 P1 验收项，也是"无 TTY 不崩"的实现手段。

## 5. 架构设计

### 5.1 分层

```text
                 ┌───────────────────────────────────────────┐
  02_code/cli/   │ nanoamp.R  ──► nanoamp_cli()  (现有)       │
                 │   ├─ call / batch / doctor / help (现有)    │
                 │   └─ tui  (新增子命令)                      │
                 └───────────────────┬───────────────────────┘
                                     │
                 ┌───────────────────▼───────────────────────┐
  02_code/R/     │ R/tui.R          ── TUI 入口与主循环      │
                 │ R/tui_state.R    ── 纯状态机（可单测）     │
                 │ R/tui_screen_*.R ── 各页面渲染（纯函数）   │
                 │ R/tui_input.R    ── 按键读取与终端控制     │
                 │ R/tui_render.R   ── 画布/表格/边框（纯函数）│
                 └───────────────────┬───────────────────────┘
                                     │  只调用公开接口
                 ┌───────────────────▼───────────────────────┐
                 │ run_haplotype_analysis() / nanoamp_cli()   │  ← 现有核心，零改动
                 │ R/correct.R · R/cluster.R · R/exact.R      │
                 └───────────────────────────────────────────┘
```

### 5.2 关键设计原则

1. **纯函数优先**。凡是不碰终端的地方（布局计算、键位派发、状态迁移、参数校验、
   表格截断）都写成纯函数，输入状态返回新状态或字符串向量。这样：
   - 可以在 `tests/testthat/` 里断言"给定 80×24 和某个 state，渲染出的行是什么"；
   - 可以做到 `R CMD check` 覆盖，而不需要真实 TTY。
2. **输入/输出与逻辑分离**。`R/tui_input.R` 是唯一碰 `stty`/`readBin`/`cat` 的模块，
   它实现一个极小的接口：

   ```r
   tui_read_key()        # -> "up" | "down" | "enter" | "esc" | "/" | "q" | "resize" | ...
   tui_size()            # -> c(width, height)
   tui_draw(lines)       # 画一帧
   tui_enter()/tui_exit()# raw mode 进出，务必 on.exit 恢复
   ```

   测试时替换成脚本化实现（喂按键序列、收集帧），即可端到端测试整个 TUI 而不需要终端。
3. **中断与恢复**。`stty` 改动必须用 `on.exit()` 恢复；`Ctrl-C` 走
   `tryCatch(interrupt=)`；X11/终端崩溃时至少留下可读的部分结果。
4. **不复制业务逻辑**。参数默认值与校验来自 `nanoamp_defaults()`；样本清单来自
   `01_data/manifest.tsv`；输出契约来自 `02_code/shared/docs/output_schema.md`。
   TUI 里不允许出现第二份"默认值表"。
5. **运行过程可观测**。运行页的阶段进度由现有日志（`log_info`）解析而来，或由
   核心提供回调；**优先选择"核心暴露回调"**而不是解析日志文本（见第 9 节阶段 P2）。

## 7. CLI 接口契约（新增部分）

```text
nanoamp tui [options]

Options:
  --plain            Force line mode (numbered menus, no full-screen rendering)
  --outdir DIR       Pre-fill the output directory
  --dataset NAME     Pre-select a dataset (as in 01_data/manifest.tsv)
  --sample NAME      Pre-select a sample
  --mode A|B|C       Pre-select a mode
  --no-color         Disable colour (also honours NO_COLOR)
  --help             Show this help
```

设计约束：

| 约束 | 说明 |
|---|---|
| 与现有子命令解耦 | `tui` 不改变 `call`/`batch`/`doctor` 的任何行为与输出 |
| 退出码 | 与现有一致：0 成功、1 任何错误（见 `cli/README.md` 现有约定） |
| 可脚本化 | 所有交互选择都必须有对应命令行选项，使 TUI 可被批处理驱动 |
| 非 TTY 安全 | 无 TTY 时自动进入 `--plain` 或明确报错，不输出乱码转义序列 |

退出码的改进（可选）：`call`/`batch` 目前所有失败都返回 1。若本方案顺带细分
（如 2=参数错误、3=缺依赖、4=分析失败），需同步改 `cli/README.md` 与文档，属**可选项**，
不在 P0 范围。

## 8. 分阶段实施计划（每阶段可独立交付、可回滚）

### P0 — 可行性验证（0.5–1 天）

**目的：先把最大的技术不确定性打掉，再谈界面。**

| 任务 | 验收 |
|---|---|
| 在真实终端里验证 `stty raw` + `readBin` 单键读取可用（Linux x86_64、macOS arm64 各一次） | 能区分 `↑`/`↓`/`Enter`/`Esc`/字母；能识别窗口 resize |
| 验证退出时终端状态被正确恢复（含 `Ctrl-C`、异常退出） | `stty -g` 前后一致；不出现"回车不回显" |
| 验证无 TTY 场景行为 | `--plain` 可用；无 `--plain` 时给明确提示 |
| 判定：是否需要"核心回调"而不是解析日志 | 给出结论并记录到 `R/tui_input.R` 顶部注释 |

**若 P0 判定 raw mode 不可靠**：立即改为"行式模式优先"，全屏渲染降为可选增强，
并在方案 v2 中调整 P1/P2 的范围。这是本方案唯一可能推倒重来的点。

### P1 — 最小可用闭环（2–3 天）

- 环境页 + 样本页 + 参考页 + 参数页（只读默认值）+ 输出页；
- 运行页：调用现有 `run_haplotype_analysis()`，显示阶段进度与日志尾部；
- 结果页：读回 `haplotypes.tsv` / `qc.tsv`，渲染 top-N 表格；
- 行式降级模式；
- 单测：渲染纯函数、键位派发、状态迁移。

**验收**：2.2 节主场景全程只用方向键 + 回车跑通；无 TTY 时不崩。

### P2 — 结果浏览与参数编辑（2–3 天）

- 参数页可编辑 + 校验（范围/类型），非法值即时提示并给出建议；
- 结果明细页（单倍型序列 + 变异逐条列出 + 95% CI）；
- 变异表页（对应 `variants.tsv`），可用 `f` 在 self/wt 结果间切换；
- 运行中断（`Ctrl-C`）安全处理与部分结果说明；
- 导出：把当前视图导出为 TSV/FASTA 到输出目录。

**验收**：改 `--min-freq` 重跑能得到与 CLI 完全一致的结果（同参数同输出）。

### P3 — 批量与预设（2–3 天）

- 批量页：多选样本 → 串行执行 → 汇总表（复用 `batch_summary.tsv` 列）；
- 参数预设的保存/载入（写到 `04_results/tui/presets/*.json`，含 `run_manifest.json` 同款的
  参数快照，便于复现）；
- **重跑上一次**（从 `run_manifest.json` 读回参数并预填）。

**验收**：批量 16 个样本跑完，汇总表与 `run_functional_tests.R` 的同类字段一致。

### P4 — 打磨与文档（1–2 天）

- 小终端/`NO_COLOR`/非 UTF-8/中文宽度对齐；
- 帮助页（模式 A/B/C 适用场景、常见问题，复用现有 README 表述）；
- `nanoamp tui` 的 `--help`、`cli/README.md`、`ARCHITECTURE.md`、根 README 同步；
- 在 macOS arm64 与本机可用的 Linux 环境各跑一次 `make test` / `make check`；
- 更新 `00_materials/work_reports/`（本方案对应的工作报告）。

**总计：约 8–12 个工作日**（按单人计，不含等待评审时间）。

## 9. 测试与验证策略

| 层次 | 手段 | 覆盖 |
|---|---|---|
| 纯逻辑单测 | `testthat`，无需 TTY | 布局计算、表格截断与宽度对齐、键位派发、状态迁移、参数校验 |
| 集成测试 | 注入脚本化输入（喂按键序列）+ 捕获帧 | "启动→选样本→跑→看结果"完整流程，用小型合成数据以秒级完成 |
| 降级测试 | 强制 `--plain`、`TERM=dumb`、`isatty=FALSE` | 行式模式可用、输出无转义序列 |
| 结果一致性 | TUI 跑出的输出与 `nanoamp call` 同参数输出逐字节对比 | 证明 TUI 没有引入第二套逻辑 |
| CI | 现有 `.github/workflows/R-CMD-check.yaml` 自动带上 | `R CMD check` 通过，测试不被跳过 |
| 人工验收 | 按 2.2 主场景在真实终端走一遍 | 体验与可理解性 |

**关键设计约束（为了可测性）**：`R/tui_input.R` 必须是全部终端 I/O 的唯一出口，
且允许被替换。凡是想在 `tui_screens.R` 里直接 `cat()` 或直接读键盘的写法，都不接受。

## 10. 风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | R 里 raw mode 按键读取在某些终端不可靠（本机验证时无控制终端，未能提前实测） | 全屏 TUI 不可用 | P0 阶段先验证；失败则行式模式优先；`--plain` 永远可用 |
| R2 | Windows 终端（旧 conhost）对 ANSI 支持差 | 姊妹仓库平台上体验差 | 本方案只承诺 Linux/macOS；Windows 明确交由姊妹仓库评估，TUI 检测到 Windows 时默认 `--plain` |
| R3 | `cli`/`crayon` 缺失 | 无颜色 | 能力探测 + 纯 ASCII 降级；两者都建议只进 `Suggests` |
| R4 | 长耗时运行中终端卡死或用户误操作 | 丢结果 | 运行页禁用会产生歧义的重绘；`Ctrl-C` 走安全中断；中间文件保留在 outdir |
| R5 | 大结果集（数千簇）渲染卡顿 | 体验差 | 只渲染视口内的行；分页；`/` 过滤；不做全量重排 |
| R6 | 中文宽度/非 UTF-8 对齐错位 | 视觉错乱 | 按显示宽度计算列宽；非 UTF-8 降级 ASCII 边框 |
| R7 | TUI 与 CLI 行为不一致 | 结果不可信 | 参数只从 `nanoamp_defaults()` 取；结果一致性测试逐字节比对 |
| R8 | 范围蔓延（TUI 变成半个基因组浏览器） | 交付延期 | 严守 1.3 非目标；P1 先交付闭环，浏览增强放 P2 |

## 11. 待确认问题

需要委托方或你确认以下几点，之后我据此把方案定稿到 v2：

1. **用户主要是谁**？如果是教授本人，P1 就足够；如果需要组内批量使用，P3 应提前。
2. **要不要保留 `--plain` 之外的"纯脚本模式"**？即 TUI 是否也需要被别的程序驱动
   （若是，则应提供 JSON 输出而非渲染文本）。
3. **是否接受把 `cli`/`crayon` 列入 `Suggests`**？虽然它们是传递依赖（实际已被安装），
   但显式声明会改变 `DESCRIPTION`。
4. **结果浏览的深度**：只看 top-N 单倍型 + QC 是否够？还是必须能看每个变异位点的
   上下文（`Seq` 列）与与公司表的逐条比对？
5. **是否需要"重跑上一次"**（从 `run_manifest.json` 复现参数）？这会影响 P3 排序。
6. **Windows**：是否确认 TUI 在 Linux/macOS 交付即可，Windows 交由姊妹仓库？
7. **是否需要在 TUI 内直接显示 `variants.tsv` 与公司 `*.变异统计表.xlsx` 的比对结果**
   （现有 `run_functional_tests.R` 已有该逻辑，但目前只在批量脚本里用）？
